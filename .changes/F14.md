# F14 — hot-swap subscription outbounds via `xray api` (no xray restart)

## What changed

`xray-sub apply` (and therefore fetch's auto-apply) no longer restarts xray
when the only change is the membership/bodies of the managed subscription
outbounds. It installs the candidate config with the pipeline's `no-restart`
mode and reconciles the RUNNING xray through the handler API:

1. `hotswap.uc plan <installed> <candidate> [prefix...] [-- ignore...]` decides
   live vs restart (rules below) and emits
   `{"remove":[tags],"add":[tags],"changed":[tags],"first_old","first_new","restart_required":null|reason,"hot_swap":bool}`.
2. Runtime guards before touching anything: `xray api lso` must answer
   (HandlerService) and the running outbound set must still equal the
   installed config.json (a hand-played `xray api` or an un-restarted manual
   edit would otherwise desync remove/add). Otherwise: restart, reason
   `api-unavailable` / `running-state-mismatch`.
3. `commit_config "" <api_before> <candidate> no-restart` (validate, snapshot,
   atomic install - no restart/verify/hooks/prune, per contract B1).
4. `hotswap_apply`: ONE `xray api rmo` with all removal tags in a JSON file
   (`{"outbounds":[{"tag":..}..]}` - a tag must never travel as a bare rmo
   argument: an argument naming a readable file is parsed as a config), then
   ONE `xray api ado` with the full bodies lifted verbatim from the candidate
   (`hotswap.uc adds`, candidate order), then verify with `lso` that the
   running set equals the candidate's tag set.
5. Any step failing -> the documented fallback: `install_config "$COMMIT_BAK"`
   + `/etc/init.d/xray restart` + `verify_or_rollback` (exactly the
   `no-restart + fallback` recipe the pipeline scenario already spells out);
   status `rolled-back`, rc 1.

Everything runs inside the mutation lock the apply command already holds; all
`xray api` children are waited for (none outlives fd 3). On success:
`pending=0`, status `applied`, `prune_backups`, stdout `ok (applied live)`.

## Plan semantics (when is a restart still required)

- **remove** = managed outbound tags of the installed config that are absent
  from the candidate or whose body changed (canonsig + the same ignore list as
  `diff.uc`), in installed order. **add** = the candidate's managed tags that
  are new or changed, in candidate order. A changed body is always
  remove+add: xray has NO alter-outbound operation (step 0.7), and all four
  managed protocols are ordinary handlers that `AddOutboundHandler` builds
  exactly like a config-file load (step 0.1).
- **changes-beyond-outbounds**: the two configs must be identical once the
  managed outbounds are removed from both (every other section + the local
  outbounds, array order included). Inbounds, routing rules, balancer config
  (selector/strategy/fallbackTag), observatory/policy config, local
  outbounds, log - none of that is reconciled by rmo/ado, so it restarts.
- **default-outbound**: the running default handler is the first outbound of
  the config xray started with; `RemoveHandler` nils it exactly when its own
  tag is removed and the first subsequent add claims it, and no API can read
  or set it. Live is allowed only when the running default provably ends up
  equal to the candidate's first outbound: if the installed first tag is
  removed, the candidate's first tag must be (re-)added - and it is added
  first, because adds run in candidate order; if the installed first tag
  survives, the candidate's first tag must be that same tag.
- Runtime reasons (shell side): `api-unavailable` (lso does not answer),
  `running-state-mismatch` (running set != installed config), plus
  `plan-unavailable` if hotswap.uc itself fails; `hot-swap-failed` with
  `fallback=1` marks a live attempt that rolled back.

## Balancers / observatory (why membership is NOT a restart reason)

`Balancer.PickOutbound` resolves its selectors through the outbound manager's
live tag map on EVERY pick (`app/router/balancing.go` -> `Manager.Select`,
whose cache is reset on every add/remove), and the observatory re-resolves
`subjectSelector` on every probe round and prunes removed tags
(`app/observatory/observer.go`, `burst/burstobserver.go`). New members start
carrying traffic after at most one probe round (leastPing/leastLoad only pick
tags that already have an Alive observation; round-robin picks them
immediately). Removing a tag that a rule still references drops that rule's
NEW connections ("non existing outTag", `app/dispatcher/default.go`) - which a
restart with the same candidate would do as well; in-flight connections
survive because `RemoveHandler` never closes the handler.

## Surfaces

- UCI `xray-monitor.sub.hot_swap` (default **1**, written to
  `files/etc/config/xray-monitor`); 0 restores the pre-F14 always-restart.
  Toggleable from the subscription tab (sub_setcfg gains a `hot_swap` param;
  no new rpcd method, the ACL already grants sub_setcfg).
- `$STATE/last-apply.json`
  `{"mode":"live"|"restart","reason":"",...,"fallback":0|1,"removed":N,"added":N,"ts":N}`
  -> status.uc -> the subscription tab shows how the last apply was applied:
  "applied live (hot-swap)" / "applied with restart" / "restart required:
  <reason>" / "hot-swap failed - rolled back" (all via `_()`).

## Tests

- `tests/run.sh`: golden plans for live / churn-only / beyond / first-outbound
  cases (+ legacy no-prefix mode), `hotswap.uc adds` payload order, unknown
  add tag rejected.
- `tests/pipeline-scenario.sh`: the xray stub now models the handler API
  (running tag set in `$STUB_API_OB`; lso/rmo/ado semantics as in xray-core:
  rmo of an unknown tag succeeds, ado fails on an existing tag). New cases:
  live apply (no restart, snapshot, running set == candidate, last-apply
  mode=live -2/+2), churn-only (zero API mutations), running-state-mismatch
  and api-unavailable (restart with reason), failing rmo (fallback restore +
  restart + verify, status rolled-back), hot_swap=0 (classic restart).
