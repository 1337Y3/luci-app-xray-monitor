# F17 — Config tab: mandatory diff preview + optimistic locking

## What

- The raw editor (`view/xray/config.js`) no longer saves directly. **Save &
  apply** first opens a modal with the diff of editor-vs-on-disk:
  - the semantic diff (added/removed/changed dot-paths, rendered with
    `XrayDiff.renderSemantic`), direction `paths_diff(on-disk, editor)` —
    "added" is what saving would add;
  - the unified text diff (`XrayDiff.renderUnified`, `-` = only on disk,
    `+` = only in the editor), old side fetched fresh at Save-click time so a
    concurrent change is visible, not diffed against a stale copy.
  - "Apply anyway" continues into the existing save flow, "Keep editing"
    cancels. Both are LuCI-native buttons; no `confirm()` anymore.
- **Invalid JSON blocks everything.** A client-side gate runs before any RPC
  call (see Decisions); `xray -test` (`config_test`, the pipeline's own gate)
  then runs in parallel with the diff calls, and a config it rejects is shown
  in the modal with "Apply anyway" disabled.
- **Optimistic locking.** `config_get` returns `hash` (md5 of the config
  bytes); the editor remembers it and sends it back as `config_save`'s
  `expected_hash`. A mismatch is refused with `ok=false, conflict=true` and a
  clear message; the UI shows it in the modal area (both when it detects the
  stale hash itself at preview time and from the server's refusal). Absent or
  empty `expected_hash` = today's behavior, so scripts and older UIs keep
  working; the UI always sends the key.

## rpcd changes (`files/usr/libexec/rpcd/xray-monitor`)

- `config_get` → `{path, hash, config}` (new `hash`; empty string when the
  config file is unreadable).
- `config_save` takes `expected_hash`; on mismatch replies
  `{ok:false, conflict:true, msg:"config changed on the router since you
  loaded it - reload and re-apply your edits"}` and touches nothing (no temp
  file, no backup, no restart). Declared in `list` and granted in the ACL.
- new `config_diff_text(config)` → the same shape as `config_diff`
  (`{added,removed,changed}` plus `error` on failure): writes the posted text
  to a temp `config.json`, proves it parses with the pipeline's own parser by
  self-diffing it (`jsondiff-cli.uc f f`), then diffs it against the live
  config. Unparseable text is named `"invalid JSON"`, not a generic failure.
  Read grant in the ACL (`config_diff_text`).

## Decisions

- **Hash = md5sum of the file bytes.** It is a change token, not a security
  digest — it only has to say "the file changed since you loaded it" — and
  `md5sum` is the applet every BusyBox build carries (cheaper than sha256 on
  this box). `config_hash()` follows a symlinked config (hashes the target,
  the same bytes `cat` shows) and returns `""` for an unreadable file, which
  makes an *absent* expected hash and an *unreadable* config behave as "no
  check" rather than locking the user out.
- **JSON validation: client-side scanner + the pipeline's own gate, in that
  order.** The client gate is one string-aware pass that strips `//` and
  `/* */` comments (outside string literals, so `"https://..."` and
  `"a // b"` values survive) and trailing commas, then `JSON.parse` — the
  same tolerance ucode's `json()` (and the fixtures) have; comments are legal
  in these configs. A first regex-based version ate a `,` inside a string
  (`"a,]"` → `"a]"`), which is why the comma handling lives in the scanner.
  Because the client cannot perfectly emulate the server's parser, the
  authoritative gate is the next step and is exact by construction:
  `config_test` (i.e. `xray -test`, what `config-save` runs anyway) and
  `config_diff_text`'s parse check, both on the router. Nothing invalid can
  produce a diff, and nothing invalid can be saved.
- **Diff direction** `paths_diff(live, edited)` mirrors the Backups tab's
  `paths_diff(current, backup)` ("restoring would add" vs "saving would
  add"), so the same renderer and wording pattern fit both.
- **The hash the UI sends is the one from load time** (page load or "Reload
  from disk"), not the fresh one from the preview call: the feature's promise
  is "no silent clobber since *you* loaded it". The preview still fetches the
  current text for the unified diff, so a foreign change shows up as `-`/`+`
  lines, and the fresh `hash` lets the UI flag the conflict before the user
  even clicks Apply.
- Residual race, accepted: the hash is checked in the rpcd script right
  before `xray-sub config-save` takes the mutation lock, so a change landing
  in those few milliseconds can still slip through. Closing it fully would
  mean teaching `xray-sub config-save` the hash (a new CLI arg and lock-held
  compare) for a window the UI flow makes unrealistic.

## Tests

- `tests/pipeline-scenario.sh` gains an rpcd-contract section: a sandboxed
  copy of the rpcd backend (its own rewrite + safety net, jshn.sh copied in,
  `$SUB` pointed at the already-rewritten xray-sub) driven through its `call`
  dispatch with stdin JSON. Covered: `list`/ACL consistency for every
  declared method, `config_get` hash (regular file, symlinked config, missing
  file) and byte-exact text round-trip, `config_diff_text` (identical text,
  a real edit, comment-only change, invalid JSON), `config_save` with the
  right hash (full pipeline: backup, install, restart, hooks), with a stale
  hash (refused, nothing touched), and with no/empty hash (backward compat).
  Skipped with a NOTE where `jsonfilter`/`jshn` are absent (not this router).
- The client-side scanner was unit-checked against 17 hand cases plus every
  fixture in `tests/fixtures/` (all parse; values stay verbatim).
- UI behavior needs a browser; see the report's manual checklist.
